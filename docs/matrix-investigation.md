# 行列3個を含む式の調査

## 引き継いだ実績

開発時の既存マクロのテスト報告では、次の結果が得られていました。
通常の分数、総和、ギリシャ文字、1個から2個の `bmatrix`、微分入りの行列は成功しています。
3個の行列を含む式では、微分記号の有無にかかわらず `OMath.BuildUp` の失敗が報告されています。
安全版では失敗した式のLaTeXが本文に残ったとの報告があります。

これらは既存版に対する利用者の報告です。
納品版の実行結果ではありません。
状態方程式をもとに代表ケースを作成しましたが、以前失敗したすべての入力の正確なバイト列、Wordビルド、入力形式は確定できていません。

微分記号のない3行列でも失敗しているため、`\dot` だけを必要原因とする説明には合いません。
ただし、行列数、式の長さ、配置、構文、入力形式、Wordのビルドを独立に変えた結果はそろっていません。
原因は未確定です。

## 公式資料が示す構文の違い

旧来のMicrosoft Support資料には、行列を `\matrix{...}` と書き、`\begin` と `\end` を使わない説明があります。
UnicodeMathについては `\matrix(a&b@c&d)` が例示されています。[Linear format equations using UnicodeMath and LaTeX in Word](https://support.microsoft.com/en-us/office/linear-format-equations-using-unicodemath-and-latex-in-word-2e00618d-b1fd-49d8-8cb4-8d17f25754f8)

一方、新しいMicrosoft Learn資料は `\begin{bmatrix}...\end{bmatrix}` を対応する行列環境として掲載しています。
新資料には4種類の区切りも記載されています。[LaTeX Support in Microsoft 365](https://learn.microsoft.com/en-us/office/math/latex)

Microsoftの2026年6月2日付の告知では、LaTeX処理を作り直したことと、当時のMac版Beta Channelでは16.110以降が対象であることが説明されています。
この告知から、利用者の環境やVBAの `BuildUp` に同じ処理が適用されているとは断定できません。[Microsoft 365 Insider Blog](https://techcommunity.microsoft.com/blog/microsoft365insiderblog/from-latex-to-accessible-pdfs-transforming-math-workflows-in-microsoft-365/4523506)

したがって、1個から2個の行列が成功したという観測を、旧資料の非対応記述だけで否定することはできません。
両資料の違いは、ビルドと入力形式を記録して比較する理由になります。
確認した [`OMath.BuildUp` の仕様](https://learn.microsoft.com/en-us/office/vba/api/word.omath.buildup)には、1式あたり2行列という上限は記載されていません。
これを根拠に、任意の個数が必ず成功するとも主張できません。

## 診断ケースと判定

| ケース | 入力の特徴 | 比較で分かること |
| --- | --- | --- |
| 1 | 2行の列ベクトル1個 | 単独の `bmatrix` が現在の経路で使えるか |
| 2 | 等号で結んだ列ベクトル2個 | 同じ基本構文を2回含む場合の基準 |
| 3 | 列ベクトル＝2×2行列×列ベクトル | 既存報告に近い3行列の再現 |
| 4 | ケース3の左辺に `\dot` | 微分記号を追加したときの差 |
| 5 | 1×1行列3個 | 3個のまま短くすると失敗が残るか |
| 6 | 3行列を `\left[\matrix{...}\right]` で記述 | 旧来のLaTeX風構文との比較 |
| 7 | 同じ3行列をUnicodeMathで記述 | 入力形式を変えたときの比較 |

ケース3が失敗してケース5が成功した場合、行列3個という個数だけでは結果を説明できません。
ケース3が失敗してケース6または7が成功した場合、行列を含むWord数式そのものより、入力文字列を構造へ変換する経路の違いが候補になります。
いずれも切り分けの推論であり、単独で内部原因を証明するものではありません。

手入力による［プロフェッショナル形式へ変換］と、診断マクロによる変換も同じ文字列で比較してください。
UIだけ成功するならVBA経路との差が残ります。
両方で失敗するなら、同じ入力形式とビルドでの構文対応も調べる対象になります。

## 今回の実装判断

変換マクロは従来の `OMaths.Add` → `BuildUp` を維持し、行列の自動分割や構文の自動置換を行いません。
部分式を別々に組版してから結合する方式は、1つの数式としての構造、積の順序、括弧、書式の維持を実機で確認できていないためです。
Wordの行列構造を直接作る方式も、LaTeXのセルや演算子の解析が必要になるため、このマクロには組み込んでいません。

現在の到達点は、失敗を本文に反映する前に検出する設計と、同じ条件で再現を調べる診断コードです。
**3行列の変換成功と、問題の根本原因は未確認です。**
今回の実機結果を次に記録します。

## Mac版Wordで実施した結果

2026年11月5日、Word 16.114（ビルド16.114.1020）で実行しました。
数式リボンはLaTeXがオン、Unicodeがオフであることを確認しました。

| ケース | 結果 |
| --- | --- |
| 1：行列1個 | 成功。生成行列数1 |
| 2：行列2個 | `BuildUp` 失敗。エラー番号 -2147467259 |
| 3：行列3個 | 同じ `BuildUp` エラー |
| 4：微分入り3行列 | 同じ `BuildUp` エラー |
| 5：最小の1×1行列3個 | 同じ `BuildUp` エラー |
| 6：旧来のLaTeX風構文 | 行列数0で構造検査に不合格 |
| 7：UnicodeMath構文 | LaTeXモードでは行列数0で不合格。UnicodeMathモードでの比較は未実施 |

この環境の結果は、参照会話の「2個は成功」という報告と一致しません。
文字列、Wordのビルド、設定の違いを分離できていないため、2個や3個を仕様上の上限とは判定しません。

別の問題として、同じ作業用文書の内容を数式から別の文字列へ繰り返し上書きすると、後続の単純な `a` でも `BuildUp` が失敗しました。
式ごとに新しい文書を作る修正後は、前後の通常式の変換と失敗後の継続が成功しています。
この修正だけでは、1式に複数の行列を含む問題は解消しませんでした。

実際の3行列の失敗式を、ギリシャ文字の式と分数の式の間に配置して一括変換しました。
成功2件、原文保持1件となり、保存したOpen XMLから、行列の元文字列とエスケープされた金額の完全一致、Word数式が2個であることを照合しました。
結果は `validation/word/matrix-recovery-result.docx` と `validation/mac-word-results.json` に保存しています。
